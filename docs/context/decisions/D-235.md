**D-235 — Performance baseline: k6 on a 20-office perf seed in its own PostgreSQL, two dashboard indexes, ranked search capped at 1,000 matches, bundle budgets in CI; search and first load still over budget** · Accepted (MVP-117, 2026-11-21)
The ticket asks for a 20-office perf seed, k6 scripts for list/get/search/dashboard/upload at 50 VUs with thresholds,
a `pg_stat_statements` review with index tuning and the top 10 plans, Lighthouse and per-route bundle budgets, results in
`docs/perf/baseline.md`. It leaves open where the load runs, how k6 gets past the per-IP rate limits and what to do with
budgets the tuning cannot meet. → **Where:** locally, never in CI (no paid service; a 5-minute run on a laptop): a second
PostgreSQL in the dev compose file under the `perf` profile (`pnpm perf:db`, port 5435, `pg_stat_statements` preloaded,
own volume), so the seed never touches dev data; k6 runs from the `grafana/k6` image (`pnpm perf:k6`). **Seed**
(`prisma/seed-perf.ts`, `nx run backend-api:seed-perf`): 20 offices × 6 users, 1k clients, 5k files, 20k READY documents
with ~80 words of text each, 10k tasks, 2k hearings, 25k timeline events, by `generate_series` so the search triggers run;
it reads only `PERF_DATABASE_URL` (Nx loads `.env`, whose `DATABASE_URL` is the dev database) and `PERF_PASSWORD`, refuses
production and a database that already holds perf offices. **Rate limits stay on:** k6 sends one `X-Forwarded-For` per
VU and iteration (the API trusts one proxy hop, `TRUST_PROXY_HOPS=1` for the run) instead of a bypass switch in the API.
**Scenarios** run one after the other, 50 VUs × 60 s each, 1 s think time; managers and lawyers alternate (the lawyer's
queries carry the assigned-scope filters); searches are half words of the seed's small vocabulary (each in ~75% of the
documents — the worst case) and half rare words or file numbers, reported apart. **Tuning** (before → after, p95 at 50
VUs): dashboard **1.71 s → 209 ms** — the quick-start existence checks (D-210) planned `LIMIT 1` as a table scan that read
every other office's rows first (50 ms on documents; worse for a new office on a big table), now ordered by the leading
column of an existing `(officeId, …)` index (0.1 ms); new index `case_timeline_events (office_id, occurred_at DESC, id
DESC)` for recent activity (12 ms → 0.3 ms), `documents (office_id, created_at)` for "new documents" (13 → 5 ms). Search
**8.1 s → 3.1 s**: `searchQuery` (D-165) now ranks only the **newest 1,000 word matches** (`RANKED_CANDIDATES`, by
UUIDv7 id) — `ts_rank` over 15k document vectors cost 0.5 s; past a thousand matches the word does not separate rows,
recency does. An office-scoped GIN (btree_gin) and an `(office_id, id)` index on `document_texts` were tried and left
out: the planner kept the office scan (the tsquery is not a constant at plan time, so its selectivity is a default 5%).
Search indexes are unchanged, so the CI test `search-query.performance.int.spec.ts` (50k rows) is not made faster by this:
its time is the 150k-row insert through the search triggers, and it passes with the cap (P95 6–75 ms). **Bundle
budgets** (`scripts/check-bundle-budget.mjs`, run in CI after the affected builds, skipped for apps not built): gzip of what
`index.html` loads and of the largest later chunk, a little above today's sizes (office app 674.5 kB initial / 125 kB PDF
viewer chunk) — a regression guard, not the 4G target. **Over budget, tracked as stories:** search at 50 VUs (common
words 3.3 s, rare 2.8 s p95; 265 / 71 ms at 10 VUs — the common words saturate the database CPU) and the office app's first
load (Lighthouse mobile slow 4G on `/login`: LCP 7.2 s, 845 KiB; desktop 1.4 s — the shell preloads the case list,
drawers and AntD table/date-picker). Lighthouse ran on the public sign-in page only: authenticated pages need the API
over https (the production build refuses another origin), i.e. staging. **Known limit:** recent activity for a user with no
files of their own (an office manager) walks every event of the office (60 ms on 25k) — within budget, revisit with growth.
No result cache (D-151, D-167): it would only answer repeated identical searches and hide new rows for a minute.
