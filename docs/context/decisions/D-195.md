**D-195 — AI evals: a synthetic AR/EN set, a local-only runner, and thresholds that gate prompt and model changes** · Accepted (MVP-89, 2026-11-21) · Builds on D-130, D-131, D-148

ai-ocr.md asks for "20 anonymized documents + reference summaries, ROUGE-L > 0.6 (EN) and a hallucinated-citation
checklist"; the Notion AI guide adds hallucination < 5 % and responses < 10 s. Silent on: the AR target, what counts as a
hallucinated citation, the schema pass rate, where the set lives and how it runs. →
**Set:** `apps/backend-api/test/ai-evals/fixtures/summary/{ar,en}.json`, 10 documents per language (pleadings, judgments,
contracts, minutes), **wholly synthetic** — invented names (marked as such: Testwood, التجريبي…), invented case numbers,
only real statute titles; never a real file, not even anonymised. Each has a reference summary; references are drafts until
the owner approves them in review, and a spec asserts every reference cites only its source.
**Runner:** `pnpm nx run backend-api:ai-evals --feature summary [--provider openai|gemini|fake]` (`test/ai-evals/run.ts`, tsx).
It runs the released `document-summary` prompt for one-call documents exactly as production does (PII redaction with the
fixture's names, one repair call, names restored) through the real provider classes, keys and models from the shell
(Zod-checked, not `AppConfig`: no database or Redis is needed). Real providers are **manual and local only**; CI runs the unit
spec with `FakeAiProvider`, never a provider. A real run writes `docs/ai-evals/<date>-<promptVersion>.md`; `--provider fake`
answers with the references and only checks the harness. Long documents (map-reduce) are out of the set for now.
**Metrics:** ROUGE-L F1 of `summary` against the reference over words after Arabic folding (`normalizeArabic`) and
Western digits; a **hallucinated citation** is an article, law (number/year) or case number (number/year) in any output
field that the source never cites (`metrics.ts` patterns, AR and EN); latency per document including the repair; cost from
`AI_MODEL_PRICES` in `Decimal`.
**Thresholds** (exit 1 on any failure): ROUGE-L mean **EN ≥ 0.6**, **AR ≥ 0.5** (provisional until the first approved
baseline; Arabic ROUGE runs lower on morphology), schema pass rate **≥ 95 %**, documents with a hallucinated citation
**< 5 %** (one in twenty fails), latency **p95 < 10 s**. **Manual gate:** a PR that adds a prompt version or changes a
model pastes a passing report (PR template section); a failing one does not ship.
Review additions (same PR): the runner reuses `AiExecutor`'s answer check and repair text (`check`,
`repairInstruction`, moved to `ai-answer.ts`) and re-checks the answer after names are restored; it reads `AI_MAX_OUTPUT_TOKENS` and
`AI_TEMPERATURE` like production; provider errors (unavailable, refused) are counted apart from the schema rate and any
one fails the run; citations are matched on folded Arabic and take plurals and lists (`Articles 74 and 80`, `المادتين 12
و13`); "section" is not a citation (contracts use it for their own clauses); a fake run is labelled HARNESS CHECK ONLY; a
report is never overwritten. ROUGE-L scores `summary` only; the citation check reads every output field. The code
(`harness.ts` `THRESHOLDS`) is the source of truth for the numbers.
Why: the same code path as production makes the score mean something, synthetic data keeps client data out of git and out
of provider logs, and a per-document citation check catches the failure lawyers cannot tolerate.
