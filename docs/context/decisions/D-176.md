**D-176 — File retainers: an append-only ledger, a locked balance, invoices paid in full** · Accepted (MVP-147, 2026-11-14) · Builds on D-017, D-162

MVP-147 left open where the ledger lives, which currency and precision it uses, who may use it, how an invoice is paid
from it and how races are stopped. → **Schema** (migration `retainer_ledger`): `RetainerEntry` (tenant; composite FKs to
the file, the invoice and the creator) with `kind` `RetainerEntryKind` DEPOSIT | INVOICE_PAYMENT, a **signed** `amount`
(deposit > 0, payment < 0, `Decimal(14,3)`, rounded to the file currency's digits as D-162), `currency` (the file's),
`paidAt`, `method`, `reference`, `invoiceId` (payments only, unique: an invoice is paid from the retainer once). CHECKs tie
the sign, the invoice and the method to the kind; the app role may not UPDATE or DELETE entries (a mistake is corrected
by a new entry — a correcting entry type is not built yet). `LegalFile.retainerBalance` becomes `Decimal(14,3)` with a
CHECK `>= 0` and **is the ledger's sum**, updated only in the transaction that writes the entry, after locking the file
row (`FOR UPDATE`): concurrent deposits and payments queue, and the CHECK is the backstop against overdraw.
`InvoicePaymentMethod` gains **RETAINER**; the timeline gains **RETAINER_DEPOSITED** (staff only, not the portal).
**One currency:** a deposit is in the file's currency (the request carries none); paying an invoice of another currency
is refused (400 `method` `validation.retainerCurrency`). **Paying an invoice:** `POST /invoices/:id/mark-paid` with
`method: RETAINER` debits the invoice's file **for the whole total** in the same transaction (INVOICE_PAID as before plus
the ledger entry and its audit row); a balance below the total → **422 BIZ-005** and nothing changes; a consolidated
invoice (no single file) → 400 `method` `validation.retainerNeedsFile`. Partial payment from the retainer is not offered.
**API:** `GET /cases/:id/retainer` → `{fileId, currency, balance, entries[]}` newest first (`view:all|assigned:invoices`),
`POST /cases/:id/retainer/deposit` `{amount, paidAt, method: CASH|BANK_TRANSFER|CARD|OTHER, reference?}` → 201 with the
retainer (`mark:invoice:paid`; an archived file → BIZ-007; more decimals than the currency → 400; a future day → 400
`validation.futureDate`). **Rights:** no new permission — the invoice rights apply (matrix unchanged), and the file must be
one whose invoices the caller may see (`InvoiceAccess.fileScope`: confidential files to the office manager and the
assigned only), else 404. Every deposit and payment is audited with the balance before and after. Review additions (same PR): the RETAINER_DEPOSITED event carries **no amount** (the timeline is read by roles without invoice rights, D-096); the file lock is `FOR NO KEY UPDATE` (only the balance changes, so timeline and document inserts on the file do not wait); paying from the retainer is refused on an archived file (BIZ-007) and for a zero total (400 `validation.retainerZeroTotal`); a deposit that would exceed what `DECIMAL(14,3)` holds is 400 `amount`, never a 500; a deposit must name its method (CHECK); the migration refuses to run while any `retainer_balance` is non-zero (no balance without ledger entries); the ledger lists the newest 100 entries (the balance covers all); audit rows carry currency, dates, reference and invoice id. **Not done:** refunds and
corrections, transferring between files, the office app's retainer card and deposit form, showing the retainer to the
portal client. Why: advance payments are tracked per file with exact money, and no race can spend the same deposit twice.
