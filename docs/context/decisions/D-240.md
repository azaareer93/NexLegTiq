**D-240 — Search under load: document search reads the office's newest 1,000 texts first; task visibility bound to the office; the 200 ms at 50 VUs needs an owner choice** · Proposed (MVP-172, 2026-11-26) · Builds on D-165, D-167, D-235
MVP-172 asks for `GET /search` p95 < 200 ms at 50 VUs on the perf seed (D-235: common words 3.3 s, rare 2.8 s) and lists
four options (per-user cache, two-step search, a RUM index, a bigger pool). → **Done, cheap to reverse:** (1) `searchQuery`
targets marked `recent` (documents only) take their word matches from the office's **newest `RECENT_WINDOW` = 1,000 texts**
first, walked in a new `document_texts (office_id, id)` index (it replaces the `(office_id)` one, its prefix); only when
those hold fewer matches than the limit does the D-235 path (newest 1,000 matches of the whole office) run — one CTE, two
branches behind one-time filters, so exactly one runs. A common word reads 1,000 rows instead of the 15k it matches
(188 → 20–25 ms, manager, warm); a rare word pays the window (~13 ms) and then the GIN path as before. Trade-off: for a word
with at least `limit` matches among the newest 1,000 texts, an older text that would rank higher is not considered (the
D-235 argument one step further: recency decides once the word does not). (2) **Task visibility** binds the file's office
to the bound office id instead of `t.office_id`: under the OR the planner hashed the subquery and read every office's files
(100k rows, 30–90 ms per search). **Measured** (k6 search scenario, 50 VUs, a shared laptop): p95 3.06 s → **1.08 s** on a
quiet machine (common 1.11 s, rare 1.04 s; 45 ms mean at 3 VUs); with other work on the machine the same code measured 3 s,
so the absolute numbers are noisy. **Still over budget:** per request the database spends ~70 ms over five group queries
(tasks 23–50 ms — the trigram pass, which the seed's 2,000 `كلمة<n>` words all match; documents 20–25 ms; files 6–15 ms),
and a pool of 40 instead of 10 made each query slower (the database CPU is the limit, not the pool). **Not chosen, for the
owner** (Jira comment on the ticket): a 60 s per-user result cache (contradicts D-151/D-167/D-235's "no cache" and hides new
rows); two-step search (titles first, document text on demand — an API/UX change); a RUM index or a bigger database
(infra). Not changed: the ranking contract (D-165), the API, the pool size.
