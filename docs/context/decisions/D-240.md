**D-240 — Search under load: two-step search (names first, document text after a pause), newest rows first for documents and tasks, a pool of 20** · Accepted (MVP-172, 2026-11-26; owner chose two-step search) · Amends D-165 (ranking: newest rows first), builds on D-167, D-172, D-235
MVP-172 asks for `GET /search` p95 < 200 ms at 50 VUs on the perf seed (D-235: common words 3.3 s, rare 2.8 s) and lists
four options (per-user cache, two-step search, a RUM index, a bigger pool). The cheap query fixes alone reached ~1.1 s;
the owner then chose **two-step search** (Jira, 2026-11-26) over a result cache (it goes against D-151/D-167/D-235) and
infra. →
**Two steps:** `GET /search?type=names` answers every group but documents (cases, clients, parties, tasks), and
`type=documents` the document text alone (`SearchQuerySchema`; `all` stays for other callers). The overlay (D-172) asks
for names after the usual 300 ms debounce and for documents once the query has also been still for another 600 ms
(`DOCUMENTS_PAUSE_MS`), so typing never sends the expensive half for a word that is not finished. Names show as soon as
they come back; the document group joins them, "Searching inside documents…" shows until it does, and "nothing found" and
the screen-reader count wait for both. "See all" asks one type as before.
**Newest rows first:** `searchQuery` targets marked `recent` (documents and tasks) take their word matches from the
office's **newest `RECENT_WINDOW` = 1,000 rows** first, walked in new `(office_id, id)` indexes (on `document_texts` it
replaces the `(office_id)` index, its prefix); only when those hold fewer matches than the limit does the D-235 path
(newest 1,000 matches of the whole office) run — one CTE, two branches behind one-time filters, so exactly one runs. A
common word reads 1,000 rows instead of the 15k it matches (documents 188 → 20–25 ms warm); a rare word pays the window
(~13 ms on documents) and then the GIN path. Trade-off: for a word with at least `limit` matches among the newest 1,000
rows, an older row that would rank higher is not considered (the D-235 argument one step further: recency decides once
the word does not). **Task visibility** binds the file's office to the bound office id instead of `t.office_id`: under
the OR the planner hashed the subquery and read every office's files (100k rows, 30–90 ms per search).
**Pool:** `DATABASE_POOL_MAX` (default 20, was pg's 10) per API/worker process — the names step runs four group queries at
once and then their re-checks, and at 50 users 10 connections queued them (p95 183 → 107–139 ms with the same queries).
API + worker = 40 connections, inside PostgreSQL's default 100; raise `max_connections` before running more processes.
**Measured** (k6 search scenario on an otherwise idle laptop, 50 VUs, each iteration names → 0.6 s → documents → 1 s):
three runs of 60 s on the final code: the first after an API restart p95 195 ms (rare 235 ms, caches and plans warming
up), then the two warm runs that are the acceptance basis, **104 ms** (common 81, rare 125) and **139 ms** (common 137,
rare 139; names step 119/166 ms, documents 100/119 ms). k6 now fails either half over 200 ms.
`search-query.performance.int.spec.ts` (50k rows per table) still passes: P95 6–73 ms (tasks "claims" 7.5 ms on the
window path). **Not changed:** the response shape, D-165's rank formula, the per-IP limit (60/min, D-167). **Known
limits:** the overlay now sends up to two requests per query — names after each 300 ms pause, documents after 900 ms —
so a slow typist, or several users behind one NAT address, reaches the per-IP limit sooner than before (still about one
request a second per person; revisit if `RATE-*` errors show up). For a word with at least `limit` matches among the
newest 1,000 rows, a group (limit 6) and its "see all" (21) may rank different candidate sets — the group the newest
rows, "see all" the whole office when the window holds fewer than 21; a shared cutoff of 21 sent most lawyers' common-word
task searches to the slow path (16 window matches of 1,000). The seed's 2,000 rare words all start with `كلمة`, so the
tasks trigram pass matches many of them; real names share fewer trigrams.
