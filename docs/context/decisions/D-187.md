**D-187 — Client uploads wait in their own table until a lawyer accepts one; accepting files it as a Document** · Accepted (MVP-99, 2026-11-16) · **Amends D-119** (no `uploadedByClientUserId` on Document) · Builds on D-003, D-126, D-158, D-186

MVP-99 asked for portal uploads as a "Document with `uploadedByClientUserId`, status pending review" (D-119 anticipated the
column). → **Model:** a tenant table `ClientUpload` (file, the grant's `clientId`, `clientUserId`, the stored object's facts,
`status` = SCANNING → PENDING_REVIEW → ACCEPTED | REJECTED, or QUARANTINED / FAILED, `rejectionReason`, reviewer, `documentId`)
instead of nullable uploader columns on `Document`. Why: `Document.uploadedById`, `DocumentVersion.createdById`, the scan
notifications, search, AI, exports and every office list assume an office author and a reviewed file; keeping unreviewed
client files out of `documents` makes "a rejected upload is visible only in the review queue" true by construction and
leaves the core entity untouched. CHECKs: key inside the office's prefix, lower-case hex checksum, a reason exactly when
REJECTED, a reviewer on ACCEPTED/REJECTED; the document FK sets only `document_id` to null on a purge.
**Portal:** `POST /portal/files/:id/uploads` (multipart `file`, the D-126 rules: type sniffing, 50 MiB, the plan's quota, file
live and not archived; **10/min**) → 202 SCANNING, audited CREATE by the portal account; the file must belong to a grant's
client (else 404, the body drained). A client's unreviewed uploads (SCANNING + PENDING_REVIEW) are capped at **250 MiB**
(422 **BIZ-027**, new; `shortcut:` constant). `GET /portal/files/:id/uploads` lists the uploads of **the grant's client** only —
another client of a shared file never sees them — with status and the rejection reason.
**Scan:** `scan-client-upload` on the `ocr` queue (ClamAV, fail closed): clean → PENDING_REVIEW and a CLIENT_UPLOAD
notification to the file's responsible lawyer; infected → QUARANTINED, object deleted, SECURITY audit; last attempt failed →
FAILED.
**Office:** `GET /cases/:id/client-uploads` (file readers), `GET /client-uploads/:id/download` (5-minute link, PENDING_REVIEW
only, audited), `POST /client-uploads/:id/accept {documentType, folderId?, name?}` and `/reject {reason ≤ 500}`
(`upload:document`, file access `contribute`): under a row lock, once (422 **BIZ-028**, new; not scanned clean → BIZ-015).
Accept creates the Document in the file's **Client Uploads** system folder unless another is given, credited to the reviewer
(the upload row keeps the client and account), PROCESSING with text extraction queued (the scan already ran), a
DOCUMENT_UPLOADED timeline event and audit rows; it is **not** shared back with the client. Reject keeps the row with the
reason the client reads and deletes the object. No timeline event before acceptance: an unreviewed file is not case history.
**Not done:** pending uploads do not count in the office's storage use until accepted (bounded by the per-client cap);
paging (newest 200); a client notification on review (the portal shows the status); the portal UI (its own story).
Review additions (same PR): accepting checks the plan's storage quota (403 AUTH-103), since pending uploads are outside
storage use; the cap is checked again inside the write under a lock on the client row, so parallel uploads cannot pass it
together, and a row still SCANNING after an hour (its scan job lost) stops counting against it (`shortcut:`); a FAILED upload's
object is deleted (the client can send it again); a file without its Client Uploads folder files the document at the root.
The CLIENT_UPLOAD notification goes to the file's responsible lawyer, whom every file has (D-140). The 10/min limit is per IP,
like every throttled route. QUARANTINED and FAILED uploads stay visible in the office's review queue (security awareness), never
downloadable. An accepted document keeps the upload's storage key (`{officeId}/{fileId}/{uploadId}/…`): deleting by the stored
key, as every purge does, covers it.
