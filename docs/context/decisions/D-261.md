**D-261 — Legal file types and sub-types are platform reference data per country, keyed by a fixed code; free-text sub-types stay as a read-only legacy value** · Accepted (MVP-175, 2026-11-28) · Supersedes the `FileType` enum of D-033/D-034
The owner decided (2026-11-27) that file types and sub-types are managed per country by platform staff, like courts;
countries stay the `Jurisdiction` enum. Until now `LegalFile.fileType` was the `FileType` enum and `subType` free text.
→ **Model.** `LegalFileType` (global, `legal_file_types`): jurisdiction, `code` (UPPER_SNAKE, unique per country, fixed once
created), `numberCode` (the `{TYPE}` of the file number, D-031; fixed once created, since it keys the office's number
counter), Arabic and English names, sort order, active flag. `LegalFileSubType` belongs to one type through its
(jurisdiction, typeCode); names unique per type. Neither is ever deleted — only deactivated — and both are read-only to
offices (global models on the scoped client); the platform admin writes them, audited (`FILE_TYPE_CREATED|UPDATED`,
`FILE_SUB_TYPE_CREATED|UPDATED`). **Files** keep `file_type` as the type's code (enum → text in place, so every value and
the 36 places that create files keep working) with a composite FK `(jurisdiction, file_type)` to the type of the file's
own country (the file's jurisdiction is the office's at creation), and `sub_type_id` with a composite FK
`(sub_type_id, jurisdiction, file_type)`, so a sub-type of another type is impossible in the database. The old
`sub_type` column stays as `legacySubType`: free text shown read-only, dropped once a sub-type is picked or cleared.
Task templates keep a type code too (no FK: they have no jurisdiction; the API checks the office's country).
**Why a code and not a uuid FK:** the type is fixed at creation (D-096: PATCH never changes it), the code is what the URL
filters (`?fileType=LITIGATION,…`, D-113) and the views already use, and an in-place column type change keeps every file's
classification with no backfill; names come from the row, so renames need no code change.
**Migration** `20261128120000_legal_file_types`: seeds the 12 former enum values for every jurisdiction (names = the
apps' `enums.fileType` labels, number codes of D-031/D-034), converts both columns, matches free-text sub-types to a
sub-type of the file's type by Arabic or English name (case and outer spaces ignored) and keeps the rest as legacy text.
**No sub-types are seeded**: no catalogue exists in the specs, so on today's data every free-text value stays legacy —
nothing is lost, and the platform admin adds sub-types per country. The search trigger (D-165) also indexes the
sub-type's names. `DROP TYPE "FileType"` is in the same migration: the API must be deployed with it (no old pod writing
the enum cast).
**Rules.** A new file needs an active type of its country and, optionally, an active sub-type of that type (400
`validation.unknownFileType` / `validation.unknownSubType`); a deactivated type or sub-type stays on the files that have
it and drops out of `GET /file-types` (active only, in order). Responses carry `fileTypeName {nameAr,nameEn}` and
`subType {id,nameAr,nameEn}`, so a deactivated one still displays. The office app labels a bare code (filters, task
templates) from that list, else `enums.fileType.<code>`, else the code. Reordering is the sort-order field.
