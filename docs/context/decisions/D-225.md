**D-225 — Production release pipeline: staging-tested images by tree match, rolling restart over two API containers; providers, domain and secrets left to the owner** · Accepted (MVP-112, 2026-11-21)
The ticket asks for a production environment (managed PG with PITR, Redis, versioned bucket, CDN, domains with HSTS, an
admin IP allow-list), `release.yml` (tag `v*` on main → reuse staging-tested images → approval → backup → migrate → rolling
restart → smoke → Sentry release + changelog), a rollback procedure and a cost estimate. No provider, region (D-021, open
on the legal-docs ticket) or domain is chosen, and choosing them commits spend. → As for staging (D-103) and backups
(D-141), the **repo side** ships now and is provider-agnostic; the providers, domain, secrets and drills are the owner's.
**Images:** nothing is rebuilt for production. A tag must point at a commit on `main` whose **tree is byte-identical to a
develop commit with a successful `staging` deployment** (GitHub deployments API); that commit's SHA-tagged images are
deployed and checked to exist. Tree matching works whether develop reaches main by a merge commit or a squash, and refuses
anything staging never ran (a hotfix straight on main lands on develop first). **Approval:** GitHub Environment
`production` with required reviewers and a `v*` tag rule (repo settings, runbook); the deploy job is **off until
`PROD_DEPLOY=true`**, so a tag before then is a free dry run of the checks. **Backup:** every migrating release first runs
the D-141 `backup.sh` (encrypted `pg_dump` to the backup bucket) from `PROD_BACKUP_ENV` and refuses to go on without it — a
provider-neutral stand-in for a provider snapshot; PITR on the managed database is the second net. **Zero downtime:**
`infra/production/compose.yml` runs **two API services `api-a`/`api-b`** (not `deploy.replicas`, which compose recreates
together) behind Caddy with active health checks and `lb_try_duration 15s`; `deploy.sh` migrates, then replaces api-a,
waits healthy + `/health/ready`, then api-b, then the worker (`stop_grace_period: 60s`; Nest shutdown hooks drain HTTP), then
reloads Caddy. A failure stops with one old container still serving. **Edge:** HSTS (2 years, subdomains) on `api.`;
`/api/v1/admin*` answers 404 outside `ADMIN_ALLOWED_IPS` at Caddy, on top of the app's `ADMIN_IP_ALLOWLIST` (D-145); the SPAs
(`app.`, `portal.`, `admin.`) are Cloudflare Pages custom domains with HSTS and, for admin, Cloudflare Access — settings,
not code. The workflow smoke-tests from outside: `/health/ready` over TLS, the HSTS header, admin 404. **Rollback:**
`workflow_dispatch` with an earlier tag — same resolution and approval, **no dump, no migration** (`SKIP_MIGRATE=1`, so an
old migrate image never meets a newer migrations table), no notes; migrations follow expand/contract (runbook) so the
previous release always reads the current schema, and a release that cannot is labelled `needs-human-review` and rolls back
by restore. **Changelog:** `gh release create --generate-notes` after a successful deploy. **Not done here:** Sentry releases
(the monitoring story owns Sentry; a step is added there), Terraform (waits for the providers, D-103), the dry run and the
rollback drill (logged in `release.md` once a host exists). Also fixed: `infra/staging/app.env.example` lacked the required
`ENCRYPTION_KEY`. **Cost:** estimated at ~$25–75/month for production at beta (runbook table, list prices to re-check).
Why: the day the owner buys the host and domain, a tag releases exactly what staging ran, with an approval, a fresh backup
and no downtime, and a rollback is one click — without committing money or a region on the owner's behalf.
