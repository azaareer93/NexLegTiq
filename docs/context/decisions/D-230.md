**D-230 — Monitoring: Sentry for the API and worker, queue metrics on /metrics, alerts as vendor rules, a PII scrub list** · Accepted (MVP-114, 2026-11-21) · Builds on D-076, D-084, D-144 · Settles D-021 for monitoring vendors (EU) · Amends D-103 (its open monitoring vendor choice is made)

The owner chose (Jira, 2026-11-10) **Sentry EU + Better Stack EU**, both listed as sub-processors, and **metric alerts as
vendor rules over `/metrics`** read by the vendor's agent; the status page waits for the domain (D-103). That answer is
the EU-region choice for these two vendors whatever D-021 settles for hosting. → **Error reporting:** `@sentry/node` in
backend-api, started in `main.ts`/`worker.ts` only when `SENTRY_DSN` (https) is set — without it nothing is initialised
and every report is a no-op, so the dependency is inert until the owner creates the account. `SENTRY_ENVIRONMENT`
(default `NODE_ENV`; staging runs `production` too) and `SENTRY_RELEASE` (the image tag). No default integrations, no
OpenTelemetry setup, no module hooks, no server name, `maxBreadcrumbs: 0`, every `dataCollection` category off: the only
events are the ones we send — **unexpected 5xx request failures** (GlobalExceptionFilter, tags `code`, `status`,
`requestId`; not SYS-002, a dependency outage, which would be one event per request and is alerted by the uptime check)
and **jobs that failed their last attempt** (TenantProcessor: `attempt >= opts.attempts`, or an `UnrecoverableError`
including an invalid payload; tags `queue`, `job`, `jobId`, `attempt`, `requestId`). Retried attempts are only logged.
The API flushes queued reports at shutdown (`ErrorReportingShutdown`), the worker after `app.close()`.
**PII scrub list (non-negotiable):** an error report never carries request bodies, headers, cookies, query strings,
tokens, the user, breadcrumbs, `extra`, job payloads, document text, or the message of any error that is not our own
`AppException` (library errors quote their input: `JSON.parse` the text, Prisma query values, decimal.js the value).
Enforced twice: (1) what is sent is a new `Error` — the type, the stack's frames only (its header repeats the message),
the message only for an `AppException` (developer-written), Prisma errors by code — never the original object or its
properties (`body`, `config`, `request`, `response`, `cause`, `meta`); (2) `beforeSend` drops `request`, `user`,
`breadcrumbs` and `extra` from every event even if an SDK upgrade starts filling them. Sentry's server-side scrubbing and
"no IP storage" are setup steps. Sentry gets less than the logs on purpose: it is an outside processor.
**Queue metrics:** `bullmq_queue_jobs{queue,state}` (waiting, prioritized, active, delayed, failed) on the API's existing
internal `/metrics`, read from Redis at each scrape with a 2 s cap per queue (queues resolved at the first scrape); a
queue Redis cannot answer for is left out of that scrape (logged) instead of failing the endpoint. **Alerts:** the rules,
severity table and status-page/post-mortem templates are in `docs/runbooks/incident.md`. Failed-job alerts (a spike; any
failed reminder) are **Sentry alerts on the `queue` tag**, not `/metrics` rules: the `failed` level is trimmed by the
30-day retention as new failures arrive, so its delta cannot count them. A dead worker (it has no `/metrics`) shows as
"jobs waiting and none active for 10 min"; there is no separate heartbeat. **Not built in-app:** an SSL-expiry script
and app-sent alerts (Better Stack's uptime monitors check certificates; option 3B was declined), the log shipper (the
Better Stack collector on the host reads the containers' JSON logs; Pino already correlates by `reqId`/`requestId`),
`/health/ready` changes (it already reports per-dependency status). **Deferred — MVP-114 is partly delivered:** Sentry in
the three SPAs (release/env tags, source maps, the same scrub list) — needs the release pipeline's build step and a DSN per
app; the `SENTRY_*` keys in the staging deploy workflow's rendered `app.env`; naming Sentry and Better Stack in the legal
sub-processor register and privacy text (the open legal-register PR #122 lists them as "not integrated yet") — **this
must happen before a DSN or collector token is set in any environment**; and the owner's account steps in the runbook's
checklist: the accounts, collector, uptime monitors with email + phone push, alert rules, the status page (before paid
launch, on the vendor's subdomain until the domain exists) and firing each test alert once.
Why: the owner's vendor choice made the SDK cheap to reverse and inert without config; reporting only final failures and
unexpected server faults keeps the free tier's quota and the signal clean; an allow-list (type, frames, our own messages)
is the only scrub that stays safe when a library changes what its errors say.
