**D-230 — Monitoring: Sentry for the API and worker, queue metrics on /metrics, alerts as vendor rules, a PII scrub list** · Accepted (MVP-114, 2026-11-21) · Builds on D-021, D-076, D-084, D-103, D-144

The owner chose (Jira, 2026-11-10) **Sentry EU + Better Stack EU**, both listed as sub-processors, and **metric alerts as
vendor rules over `/metrics`** read by the vendor's agent; the status page waits for the domain (D-103). → **Error
reporting:** `@sentry/node` in backend-api, started in `main.ts`/`worker.ts` only when `SENTRY_DSN` (https) is set —
without it nothing is initialised and every report is a no-op, so the dependency is inert until the owner creates the
account. `SENTRY_ENVIRONMENT` (default `NODE_ENV`; staging runs `production` too) and `SENTRY_RELEASE` (the image tag).
No default integrations, no OpenTelemetry setup, no module hooks, `maxBreadcrumbs: 0`, every `dataCollection` category off: the only
events are the ones we send — **5xx request failures** (GlobalExceptionFilter, tags `code`, `status`, `requestId`) and
**jobs that failed their last attempt** (TenantProcessor: `attempt >= opts.attempts` or `UnrecoverableError`; tags
`queue`, `job`, `jobId`, `attempt`, `requestId`). Retried attempts are not reported (the queue metrics count them).
**PII scrub list (non-negotiable):** an error report never carries request bodies, headers, cookies, query strings,
tokens, the user, breadcrumbs, `extra`, job payloads or document text. Enforced twice: (1) what is sent is a new `Error`
built from `loggableError` — the same fields the logs keep (type, message, stack of unexpected errors; Prisma errors by
code only, since their message quotes query values; never the original object or its properties such as `body`,
`config`, `request`, `response`, `command`); (2) `beforeSend` drops `request`, `user`, `breadcrumbs` and `extra` from every
event even if an SDK upgrade starts filling them. Sentry's own server-side scrubbing and "no IP storage" are setup steps.
**Queue metrics:** `bullmq_queue_jobs{queue,state}` (waiting, active, delayed, failed) on the API's existing internal
`/metrics`, read from Redis at each scrape with a 2 s cap per queue; a queue Redis cannot answer for is left out of that
scrape (logged) instead of failing the endpoint. Alert rules (error rate, P95, queue waiting, failed-job spike, any failed
reminder, disk, SSL < 30 days, uptime) are written in `docs/runbooks/incident.md` and configured in Better Stack, with the
severity table and status-page/post-mortem templates. **Not built in-app:** an SSL-expiry script and app-sent alerts
(Better Stack's uptime monitors check certificates; option 3B was declined), the log shipper (the Better Stack collector on
the host reads the containers' JSON logs; Pino already correlates by `reqId`/`requestId`), `/health/ready` changes (it
already reports per-dependency status). **Deferred (follow-ups):** Sentry in the three SPAs with source-map upload (needs
the release pipeline's build step and a DSN per app), setting the `SENTRY_*` keys in the staging deploy workflow's
rendered `app.env`, and naming Sentry/Better Stack in the legal sub-processor register — that must happen before a DSN or
collector token is set in any environment.
Why: the owner's vendor choice made the SDK cheap to reverse and inert without config; reporting only the final failure and
only server faults keeps the free tier's quota and the signal clean; building the PII guard from the log's existing
allow-list means one rule for both sinks.
