**D-266 — Courts are platform reference data per country, managed in the admin panel; offices pick active courts of their country and report missing ones; office courts become read-only legacy rows that admins replace or promote** · Accepted (MVP-167, 2026-11-28) · Amends D-115 (supersedes its owner-review step and the office court writes)
The owner decided (2026-11-27) that the seeded list is development data, courts are managed per country by platform staff,
offices see the courts of their own country (`Office.jurisdiction`) and can no longer add courts: they report a missing
one. Countries stay the `Jurisdiction` enum. → **Model.** `courts.is_active` (default true): a deactivated court drops out
of the office picker and of new assignments, and stays on the files and sessions that have it. New tenant model
`CourtReport` 🔒 (`court_reports`): office, reporting user (composite FK), name, city?, note?, `status`
(`CourtReportStatus` = `PENDING | ADDED | DISMISSED`), the platform court added for it (`court_id`), the admin who resolved
it, `resolved_at`, `dismiss_reason`. Office rows of `courts` (`office_id` set) stay where files, sessions and judges use
them, read-only.
**Office API.** `GET /courts` lists only **active platform courts of the office's country** (the `jurisdiction` query
parameter is gone); `GET /courts/:id` and the judge routes still read any court the office sees (a legacy office court or a
deactivated one on an old file). `POST/PATCH/DELETE /courts` are removed. A **newly assigned** court of a file or session
must be an active platform court of the office's country, else 400 VAL-001 `validation.unknownCourt`; a court the row
already has (also the one an outcome's next hearing carries over) is kept as is. Judges are unchanged (an office still adds
its own judge to a court). `POST /court-reports {name, city?, note?}` (`create:case` or `create:session`, like the old court
write; office audit row) records a request.
**Admin API** (platform realm, D-145; audited in `platform_audit_logs`). The admin realm has no permissions of its own —
every platform admin is a full admin (D-145) — so "its own permission" is the realm: an office token never reaches these
routes, an admin token never reaches the office ones. `GET/POST admin/courts`, `PATCH admin/courts/:id` (platform courts of a
country, inactive included; `isActive` deactivates; the jurisdiction is fixed once created, English name required as before —
the platform unique key); `GET admin/office-courts` (office rows with office name and file, hearing and judge counts);
`POST admin/office-courts/:id/replace {courtId}` re-points that office's files and sessions **and moves its judges** to a
platform court of the same country, then deletes the office row; `POST admin/office-courts/:id/promote {nameEn?}` turns the
row into a platform court (English name required if missing; 409 RES-002 if the country already has one by that name);
`GET admin/court-reports?status`, `POST admin/court-reports/:id/add` (creates the platform court in the office's country and
links it) and `POST admin/court-reports/:id/dismiss {reason?}` — once (422 **BIZ-029**, new, "court report already
resolved"). The reporting user then gets an in-app notification (`COURT_REPORT_RESOLVED`, category FILES, D-149: queued in
the office's tenant context after the commit).
**Integrity.** D-115's triggers forbid a court changing office and a judge changing court. Replace and promote need exactly
that, so `nlq_reference_owner_fixed()` lets it through only when the transaction set `nlq.court_merge = 'on'`
(`set_config(…, true)`, local to the admin transaction); every other write still fails. Replace runs in one transaction:
judges first (so the file and session triggers then find the judge at the new court), then `legal_files` and `sessions`
(raw SQL by `office_id` and `court_id`, so `updated_at` and the search index are untouched and no other office is
reached), then the delete.
**Seed.** `courts.seed.ts` stays as development and demo data: `seed-demo`, `seed-perf` and the dev `seed` target load it;
the migrate image's `seed.js` seeds plans only, so production starts with no courts and admin edits are never overwritten.
D-115's list of names for the owner to check is now the admins' job, not code.
**Why** one platform list per country instead of each office's own: consistent names across offices (reports, future
court-process data), no duplicates per office, and the platform owns corrections. Office rows are kept, not converted by
the migration, because which platform court an office meant is a human call.
